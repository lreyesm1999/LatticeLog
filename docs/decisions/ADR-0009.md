# ADR-0009 — Remote ingest protocol v1 and deduplication · accepted (2026-11-18)

## Context

P16 asks to receive events from many applications **while keeping local storage an option**, with retries, verifiable
ACKs, and no silent duplicates or false confirmations (gate G16). The SDK already has a durable local store, with dense
per-store sequences, crash recovery and a quota that never deletes.

## Decision

1. **The local store is the spool.** Applications write with the usual logger to their local store. A `Forwarder`
   reads that store and sends the records to the server. A network or server outage loses nothing: records stay on disk
   until the server confirms them. A full spool is the local store's quota, which fails explicitly and is counted
   (`DroppedWriteError`); it never deletes (P16-T07/T08).
2. **Idempotency key = (`producer_id`, local sequence).** `producer_id` is the local store's `store_id` (128 bits).
   Local sequences are dense and increasing. The server keeps, per producer, the last confirmed number
   (`committed_through`). Anything below it is dropped as a duplicate, an overlap is trimmed, and a gap is rejected
   unless the client declares it (P16-T04). This deduplicates per event, not just per batch, and two different events
   are never confused.
3. **Deduplication state comes from the stored data.** Every batch is stored with an `ingest` context
   (`ingest.producer`, `ingest.first_local_seq`) on top of each record's original context. After a crash, the server
   recomputes `committed_through` by counting the records of each batch that **did** survive, starting from an optional
   checkpoint. There is no second file that could drift from the data.
4. **Transport: HTTP (1.1 and 2) with one `POST` per batch** (`/v1/ingest`), no gRPC (P16-T01). It works with
   `HttpClient` and Kestrel with no new SDK dependencies, goes through proxies and load balancers, and can be debugged
   with common tools. A batch travels in a single request and there is one batch in flight per producer, which keeps
   ordering.
5. **Binary envelope + negotiable body** (P16-T02/T09). A fixed 48-byte header carries the producer, local sequence
   range, record count, encoding, compression, lengths and CRC-32. The v1 body is `latticelog.jsonl`, the lossless
   exchange format already tested, optionally gzipped. The encoding field leaves room for a binary `.llog` body later
   (added as `body_encoding = 2`): a server that does not know an encoding answers 415 with the ones it accepts.
6. **ACK = the level actually reached** (P16-T05). The client asks for `fsync` (default) or `os`. The server confirms
   with *group commit*: several requests share one fsync. The response states the level reached and up to which local
   sequence the data is confirmed. No replication in the ACK path; the `replicas` field is reserved.
7. **At-least-once on the wire, exactly-once effect in the server's store** for a given producer (P16-T03). Nothing is
   promised across producers, or if the producer's local store is lost.
8. **Security from the start** (P16-T10..T12):
   - **Authentication:** per-client *bearer* tokens. The server stores only their SHA-256, compares in constant time and
     re-reads the tokens file when it changes, so tokens rotate without a restart. Each token can be restricted to
     certain producers.
   - **TLS:** required off loopback, unless an explicit, insecure option is set.
   - **Limits:** request size, decompressed size, compression ratio (anti-bomb), records per batch and bytes per line.
   - **Quotas:** per-token quota (records/s) and a bounded write queue, answering 429/503 + `Retry-After`.
9. **Retries** (P16-T06): exponential backoff with full jitter (200 ms base, 30 s cap), honouring `Retry-After`.
   400/401/403/unresolved 409/413/415 errors are not retried: they are reported.

## Rejected alternatives

- **gRPC**: adds Grpc.Net.Client, protobuf and code generation to every SDK, when the body already has its own format.
  It can be reconsidered for streaming if the P16-T14 measurements justify it.
- **Deduplicating only by batch id**: does not cover batches that are split differently after a client restart.
- **A deduplication checkpoint as the only source**: any window between persisting the data and writing the checkpoint
  would produce duplicates after a crash.
- **Global exactly-once**: needs a full transaction protocol; it is not promised.

## Consequences

- A record reaches the server at least one `poll interval` after it is written locally (shipping latency, not logging
  latency).
- The server adds an `ingest` context to every record: it is provenance and it is documented. The rest of the record is
  stored exactly as on the producer.
- If the local store is lost before shipping, those records are lost (P16-T15). To lose nothing when the producing
  machine fails, use `Durable` locally plus an `fsync` ACK on the server.
